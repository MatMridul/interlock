## What is in the repo
- **Specs:** `.kiro/specs/gate/{requirements,design,tasks}.md`. Requirements in EARS form, design with the invariant-to-test map, tasks with done items ticked. These three files were drafted at the end of the build from `SPEC_GATE_v2.md` and the reports, not generated by Kiro's spec workflow (owner to confirm; if the owner re-generates them in Kiro, update this line).
- **Steering:** `.kiro/steering/product.md` (honesty rules), `tech.md` (generated-table rule, import rule, how to test), `security.md` (no secrets). All `inclusion: always`.
- **Hook:** `.kiro/hooks/policy-checks-on-save.json`. On save of `policy/finance_table.json` or `policy/finance.jff` it runs the exhaustive and mutation checks and `gen_executor_table.py --check`. The trigger name and matcher were checked against the docs only, not run inside Kiro (unverified).
- **MCP:** `.kiro/settings/mcp.json` binds a JFLAP MCP server (`jflap_mcp.py` from `jflap-cli`, auto-approving six read-only tools). In the recorded verification the same code was called through the CLI, not through the MCP server (docs/reports/VERIFICATION_REPORT.md). Owner to confirm whether Kiro itself called the MCP tools.
- **Property-based testing:** Hypothesis tests we wrote (`tests/test_gate_properties.py`, 300 examples per property, plus guard properties). Kiro's own PBT "Correctness" feature is IDE-only and was not used.

## Two agents, kept apart
Kiro is the dev-time agent. The Strands agent in the app is the runtime agent. Kiro hooks do not gate the runtime agent; the Gate does.

## Moments where the process mattered

**The spec gate corrected v1.** Before any code, `SPEC_GATE_v2.md` replaced claims in the first spec: "0.2ms JFLAP proof latency", "zero hallucination", "JFLAP intercepts every action at runtime". JFLAP is build time; the runtime is a generated table. It also added two invariants the first draft lacked: MFA is human-only (INV-11) and a checker failure never lets a tool run (INV-12), and it noted that Strands runs a turn's tool calls concurrently by default, so the agent uses `SequentialToolExecutor`.

**Verification first.** The build order put the hardest invariant first. The state machine was checked three independent ways (table, ordering rules, regex) over all 2,015,539 strings up to length 8, then in JFLAP (deterministic, complete, minimal, equal to a second machine built from flags), and 96 of 96 single-cell mutants were caught, all before the executor existed.

**A mutation survivor became a property.** Injecting `DRAFTED -DRAFT-> DRAFTED` into the Gate survived S1 to S7: no stated property forbade two drafts in a row. We added property X1 (`test_x1_no_stacked_drafts`), and with it all 12 gate mutants are killed.

**A guard that was off by default.** The argument guard first shipped off by default so the existing tests kept passing; only the server turned it on. That left a trap for any caller who forgot. It was flipped: `Gate()` now enforces the guard, tests that needed it off pass `guard=False` explicitly, and a new test pins the default.

**Bedrock access and the fallback.** Claude Haiku 4.5 was blocked in two regions by the Anthropic use-case-details form. Every successful real call used Amazon Nova 2 Lite in ap-south-1. The real adversarial run therefore describes Nova's behaviour, not Claude's, and the reports say so. In one run Nova tried `execute_transfer` after a prompt-injection style message and the hook cancelled it.

## What we did not do
No Kiro PBT, no Kiro PreToolUse hook on our own tool calls (its STDIN fields were never read), no deployment yet.
