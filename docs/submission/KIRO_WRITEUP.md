## How it was built: a Kiro Crew bot directing helper sessions

The project was built by a Kiro Crew bot (the conductor) that handed small work items to helper sessions. This is how it ran, and it can be checked in the git history and the reports:

- **One conductor, small work items.** Each item had a title and an acceptance file (a report or a test result) that had to exist before the item counted as done. Commit messages are 5 to 7 words, many small commits (171 commits at the time of writing).
- **Every report was reviewed.** A helper's "done" was treated as a claim. The conductor read the report and re-ran or spot-checked its numbers before accepting. The reports in `docs/reports/` are those records, including what each helper did not check.
- **One task list.** [OPEN_TASKS.md](../OPEN_TASKS.md) is the only list of planned work; helpers did not edit it, the conductor did.
- **Different agents at dev time and at runtime.** The Kiro agents build and verify the project. The Strands agent inside the app is a separate runtime agent, and Kiro hooks do not gate it. The Gate does. The one place Kiro itself is gated is Safe Ship, below.
- **Kiro Crew versus CLI versus IDE.** Crew ran the work: planning, dispatching items, collecting reports. The CLI was where Kiro features were tested live (hooks, custom agent, MCP), because it can run non-interactively and leaves transcripts. The IDE was not used in any recorded run (**owner to confirm**). Crew's own agent was not tested against the Safe Ship hook ([SAFE_SHIP.md](../SAFE_SHIP.md), tasks 11 and 12).

## Specs: spec-driven development versus vibe coding

- **Spec first for the core.** [SPEC_GATE_v2.md](../../SPEC_GATE_v2.md) was written and approved before the gate code (2026-11-19, see [tasks.md](../../.kiro/specs/gate/tasks.md) item 1). It fixed the 12 invariants and the build order. `.kiro/specs/gate/{requirements,design,tasks}.md` were then written from it and the reports, in Kiro's three-file format. They were not generated by Kiro's spec workflow in the IDE (**owner to confirm** if the owner regenerates them there).
- **Spec for Safe Ship.** [.kiro/specs/safe-ship](../../.kiro/specs/safe-ship) has requirements, design and a tasks file with ticked items, and open items marked open (IDE run, Crew run, `fs_write` payloads, power install).
- **Exploration first for the UI.** The look was not specified up front. Four HTML comps were built and compared ([ROUND_1.md](../ui-v2/ROUND_1.md), [ROUND_2.md](../ui-v2/ROUND_2.md), `docs/ui-v2/comps/`) before the React build. That part was closer to vibe coding: look, react, adjust.
- **What the difference changed.** Where there was a spec, the tests came from it (the invariant-to-test table in the design file). Where there was none, we found problems late, for example the layout overlaps and the motion bug below.

## Hooks

- **Save hook** [policy-checks-on-save.json](../../.kiro/hooks/policy-checks-on-save.json): on save of the policy table or `.jff`, runs the exhaustive and mutation checks and the table freshness check. **Never fired inside Kiro.** The trigger name `PostFileSave` matches the docs ([SAFE_SHIP_SPIKE.md](../spikes/SAFE_SHIP_SPIKE.md) section 1) but nobody saved a file in Kiro to see it run (**owner to confirm**, task A10).
- **Safe Ship `PreToolUse` hook** [safe-ship.json](../../.kiro/hooks/safe-ship.json) (disabled by default, turned on locally by `python scripts/safe_ship.py enable`): runs `safeship/hook.py`, which feeds each Kiro tool call to the same `Gate` class the finance policy uses. **Verified live on Kiro CLI 3.5.0**: a push after an edit was refused (exit 2, the message went back to the agent, which quoted it and did not work around it); after a green test run the push was allowed; after another edit it was refused again. Evidence: [safe_ship_live_decisions.jsonl](../evidence/safe_ship_live_decisions.jsonl), [safe_ship_live_recheck.md](../evidence/safe_ship_live_recheck.md), [safe_ship_live_transcript.txt](../evidence/safe_ship_live_transcript.txt). One recorded run, two model invocations, a scratch repo with a local remote (nothing went to GitHub). The UI replays this recording under Policy: safe-ship, and runs no hook in the browser.
- **Limits:** only mapped tools and commands are checked; `fs_write`, `fs_append` and `execute_bash` payloads were never seen live; parallel tool calls in one turn have no defined order ([SAFE_SHIP.md](../SAFE_SHIP.md)).

## Custom agent

[.kiro/agents/gate-verifier.json](../../.kiro/agents/gate-verifier.json): a read-only verifier (file writes denied, only `python -m pytest tests/*` and `gen_executor_table.py` allowed in the shell) that runs the exhaustive and mutation checks, the freshness check and two JFLAP MCP calls. It was run three times with `kiro-cli chat --no-interactive --agent gate-verifier`, and all three transcripts are kept: run 1 was denied a shell command and stopped, run 2 passed the tests but had no permission for the MCP tools, run 3 passed after the permission rules were fixed ([gate_verifier_runs.md](../evidence/gate_verifier_runs.md)). It ran the `safe_ship` policy only, not `finance`. Its permission rules were not tested against a hostile prompt.

## Property-based testing

Hypothesis properties we wrote: `tests/test_gate_properties.py` (S1 to S7 and X1, 300 examples each), guard properties, and the Safe Ship engine properties in `tests/test_safe_ship_engine.py`. Kiro's own property-based testing feature is IDE-only and was not used.

## Moments where the process mattered

- **The spec gate corrected v1.** Before any code, SPEC_GATE_v2 replaced three claims of the first spec ("0.2ms JFLAP proof latency", "zero hallucination", "JFLAP intercepts every action at runtime"). JFLAP is build time; the runtime is a generated table. It also added two invariants the first draft lacked (MFA is human-only, INV-11; a checker failure never lets a tool run, INV-12) and noted that Strands runs one turn's tool calls concurrently by default, so the agent uses `SequentialToolExecutor`.
- **A mutation survivor became a property.** Injecting `DRAFTED -DRAFT-> DRAFTED` into the Gate survived properties S1 to S7: nothing forbade two drafts in a row. We added X1 (`test_x1_no_stacked_drafts`); all 12 gate mutants are then killed ([EXECUTOR_REPORT.md](../reports/EXECUTOR_REPORT.md)).
- **A guard that was off by default.** The argument guard first shipped off so existing tests kept passing, and only the server switched it on. Any caller who forgot got no guard. It was flipped: `Gate()` enforces the guard, tests that need it off pass `guard=False`, and a test pins the default.
- **Headless Chrome defaults to reduced motion.** The first motion screenshots showed nothing moving, because the headless browser reported `prefers-reduced-motion`. Found in the motion review ([UX_BASICS_REPORT.md](../ui-v2/UX_BASICS_REPORT.md)); the capture was redone against a slowed stub.
- **DynamoDB on-demand has no free tier.** The deploy brief assumed on-demand capacity. Reading the pricing page showed only provisioned capacity is in the always-free allowance, so the plan uses a provisioned table at 20 read and 20 write units ([DEPLOY_PLAN.md](../deploy/DEPLOY_PLAN.md), assumption 10).
- **The Bedrock Claude use-case form.** Claude Haiku 4.5 failed with the Anthropic use-case-form error in ap-south-1, and in one call in us-east-1 (the conductor saw it work once from the same machine; the cause was not found, [STRANDS_REPORT.md](../reports/STRANDS_REPORT.md)). Every successful real call, including the 91 calls of the race benchmark, used Amazon Nova 2 Lite in ap-south-1, and the reports say so ([RACE_REPORT.md](../reports/RACE_REPORT.md), [STRANDS_REPORT.md](../reports/STRANDS_REPORT.md)).

## What we did not do

No Kiro PBT, no Kiro Web, no IDE run (owner to confirm), no power install, no live test of the Safe Ship hook in the IDE or in Crew's own agent, no deployment (the Lambda and DynamoDB plan is written; nothing was created on AWS).

One limit worth naming: both policies are regular languages (DFAs). Policies that need counting or nesting would need a pushdown automaton; JFLAP supports those and we vendored its CLI, but we built no PDA policy.
